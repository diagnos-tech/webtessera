# ADR-0025: Verify Ed25519 signatures with RFC 8032 semantics (`zip215: false`), not noble's default

- **Status:** superseded by ADR-0206
- **Date:** 2026-08-19
- **Author:** note contributor
- **Upstream reference:** `golang.org/x/mod/sumdb/note/note.go`, Go's `crypto/ed25519`

## Context

`sumdb/note`'s verifier is one line of Go:

```go
v.verify = func(msg, sig []byte) bool {
	return ed25519.Verify(key, msg, sig)
}
```

Go's `crypto/ed25519.Verify` implements **RFC 8032 / FIPS 186-5** verification: it rejects a
signature whose length is not 64, rejects a non-canonical scalar `S`, decodes `R` and `A`
canonically, and checks the cofactorless equation `[S]B = R + [k]A`.

`@noble/curves` defaults to something else. Its own documentation says so:

```js
const isValid = ed25519.verify(sig, msg, pub);              // ZIP215
const isValid2 = ed25519.verify(sig, msg, pub, { zip215: false }); // RFC8032 / FIPS 186-5
```

ZIP215 and RFC 8032 do not accept the same set of signatures. ZIP215 is deliberately more
permissive around small-order and non-canonically-encoded points, so that batch and single
verification agree and so that consensus systems cannot be split by an adversarially chosen
signature. That is the right default for a blockchain. It is the wrong default here.

A transparency log's entire security argument is that every participant — log, witnesses,
monitors, clients — reaches the *same* verdict on the same checkpoint. If this port accepted a
checkpoint signature that Go's `sumdb/note` rejects, then a webtessera client and a Go witness
looking at the same bytes would disagree about whether the log had signed them. An attacker who can
produce such a signature gets a checkpoint that one half of the ecosystem trusts and the other half
does not, which is exactly the split-view attack the log exists to prevent.

The second difference is behavioural rather than cryptographic: Go's `Verify` **returns false** for
a malformed signature, where noble **throws**. Upstream's `TestOpen` depends on the former. Its
"invalid signature" case splices four base64 characters into a signature line, producing a 67-byte
signature, and requires:

```
invalid signature for key PeterNeumann+c74f20a3
```

An uncaught throw there would escape `open` as something that is neither `InvalidSignatureError` nor
`errMalformedNote`, and a caller switching on the error type would take the wrong branch — most
likely treating a corrupt signature as a transport failure and retrying, rather than as an attack.

## Decision

`newVerifier` builds its verify closure as:

```ts
try {
	return ed25519.verify(sig, msg, keyData, { zip215: false });
} catch {
	return false;
}
```

`zip215: false` is passed explicitly and is not to be removed as "the default anyway" — it is not
the default. The `catch` converts noble's throw for a malformed signature or a non-point public key
into `false`, which is what Go's `Verify` returns for both.

No curve or hash arithmetic is written by hand, per ADR-0005.

> **Reviewer correction (2026-08-19, note reviewer) — `zip215: false` alone is not sufficient.**
> `zip215: false` fixes the *point-canonicality* half of the gap, but not the *cofactor* half.
> `@noble/curves`' `verify` checks the **cofactored** group equation `[8](R + [k]A − [S]B) = O` in
> *both* zip215 modes; Go's `crypto/ed25519` is **cofactorless** (`R == [S]B − [k]A` exactly, by
> byte comparison of the recomputed `R`). The two disagree for **mixed-order public keys**: a
> signature whose verification residual is a non-zero small-order point is accepted cofactored and
> rejected cofactorless. This was demonstrated with a concrete vector accepted by
> `ed25519.verify(sig, msg, pub, { zip215: false })` and rejected by Go 1.25.5's
> `crypto/ed25519.Verify` (see the Review section). Left unfixed, this is a split-view hole: a
> webtessera client would trust a checkpoint a Go witness rejects.
>
> The shipped verifier therefore keeps `zip215: false` as the canonicality gate and **adds a
> cofactorless confirmation**: it recomputes the residual `R + [k]A − [S]B` from noble's own
> `Point` primitives and `@noble/hashes`' `sha512`, and requires it to be exactly the identity.
> It also rejects `S >= L` explicitly (`SetCanonicalBytes` in Go). No field or curve arithmetic is
> hand-written — only noble `Point` operations and a little-endian scalar decode are composed, which
> ADR-0005 permits. The helper is `verifyEd25519` in `note.ts`; it was cross-checked against Go's
> `crypto/ed25519.Verify` over 821 vectors (400 honest, 400 corrupted, 20 mixed-order, 1
> wrong-length) with zero disagreements, and a regression test pins the mixed-order vector.

> **Update (2026-10-02): this ADR's description of Go is wrong, and it is superseded by ADR-0206.** Go 1.24 and
> 1.25's `crypto/ed25519` decode the public key with `edwards25519.Point.SetBytes`, which accepts
> non-canonical encodings of curve points, and do not reject small-order public keys; only `S` must be
> canonical, and `R` is compared as bytes with the canonical encoding of `[S]B − [k]A`. So "decodes `R` and `A`
> canonically" and "no small-order A" above do not describe Go, and the shipped verifier (noble's
> `zip215: false` gate plus the residual check) rejected signatures Go accepts: under every small-order key and
> every non-canonically encoded key. The note/gostd audit found 78 such vectors among 2,366, and none in the
> other direction. `verifyEd25519` is now a transcription of Go's `verifyWithDom` and agrees with Go on all
> 2,366; degenerate keys are refused instead when a verifier is configured (`newVerifier`), as a documented
> fail-closed divergence.

## Consequences

- The port accepts exactly the signatures Go's `sumdb/note` accepts, which is the only acceptable
  answer for a checkpoint verifier.
- `zip215: false` is marginally slower than the default in noble, because it performs the canonical
  encoding checks. Signature verification is not on any hot path — a checkpoint carries a handful of
  signatures, not thousands.
- The `catch` is a bare `catch { return false }`, which normally deserves suspicion. Here it is the
  translation of a documented Go behaviour, and the comment at the call site says so. It cannot mask
  a programming error: the only inputs are a public key already length-checked by `newVerifier` and
  a signature blob from the wire.
- If `@noble/curves` ever changes its default, this code is unaffected, because the option is
  explicit.

## Alternatives considered

- **Use noble's default (ZIP215).** Rejected: accepts signatures Go rejects, which is a split-view
  risk on the exact function that decides whether a log signed a checkpoint. This is the wrong
  direction to be lenient in.
- **Length-check the signature before calling noble, instead of catching.** Rejected as
  insufficient: noble also throws for a public key that is not a valid curve point, and a
  length-check-plus-catch is the same code with an extra branch that can drift out of sync with
  noble's validation.
- **Let the throw propagate and document it.** Rejected: it changes `open`'s error contract, breaks
  upstream's test, and gives callers a third failure mode Go does not have.
- **Verify with WebCrypto for RFC 8032 semantics.** Rejected under ADR-0005: async, and its Ed25519
  support is uneven across the runtimes this has to run in.

## Review

- **Reviewer:** note reviewer (independent)
- **Verdict:** approved, with a blocking defect found and fixed during review
- **Notes:**
  - **Read in full against the Go source**: `crypto/ed25519/ed25519.go` (`Verify` →
    `VerifyWithOptions`) and `crypto/internal/fips140/ed25519/ed25519.go` (`verifyWithDom`), which is
    where `sumdb/note`'s `ed25519.Verify(key, msg, sig)` bottoms out. Confirmed Go is cofactorless:
    it computes `R' = [S]B − [k]A` via `VarTimeDoubleScalarBaseMult` and does
    `bytes.Equal(sig[:32], R'.Bytes())`, with `SetCanonicalBytes` enforcing `S < L` and `SetBytes`
    enforcing canonical `A`. Also read `@noble/curves@2.0.1` `abstract/edwards.js` `verify`: it ends
    in `RkA.subtract(SB).clearCofactor().is0()` — cofactored — in both zip215 modes, and `abytes`
    throws for a non-64-byte signature *before* the inner try/catch, which is why the outer
    `try/catch → false` is genuinely required.
  - **Defect (blocking, would have shipped):** the as-written `zip215: false`-only verifier accepts
    signatures Go rejects, for mixed-order public keys. Verified empirically, not by argument:
    - vector — `pub = 678c8edde71e8f4dd2d05c673807d7951ab5e93763a16363f14a1812c7bd8fac`,
      `msg = "hi"`,
      `sig = 032bc2b7e1cf18bd44686ac76094ea4c80547a461de1dea46055e5059f8df8dfb65ed101a84ad476d3b3715c03644f9564a48c92b0d84ea8ae9736cd99e59005`.
    - `ed25519.verify(sig, msg, pub, { zip215: false })` → **true**;
      Go 1.25.5 `crypto/ed25519.Verify(pub, msg, sig)` → **false**.
  - **Fix applied (per REVIEW-PROTOCOL §3):** `verifyEd25519` in `note.ts` now adds a cofactorless
    residual check and an explicit `S < L` reject on top of noble's canonicality gate. Cross-checked
    against Go over 821 vectors (400 honest, 400 corrupted, 20 mixed-order, 1 wrong-length): Go and
    the fixed verifier agree on every one (both accept exactly 402). Regression test added:
    `note_test.ts` › "rejects a signature valid under noble's cofactored rule but invalid under Go's
    (RFC 8032)", which also asserts noble accepts the vector under both zip215 modes so it cannot
    pass vacuously. Full suite green (1224 tests), `tsc --noEmit` clean.
  - The decision's *intent* — match Go's RFC 8032 / FIPS 186-5 accept/reject set — is correct and is
    now actually achieved. The `catch → false` mapping for malformed signatures is faithful to Go.
